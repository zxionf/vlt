1. 服务器存储设计原则
   不存任何明文或可解密信息：密码记录在客户端用 Data Key 加密后上传，服务器只保存密文。

Data Key 用各设备公钥加密分发：每个设备有一对 RSA 密钥，Data Key 的密文分别存储，仅目标设备能解密。

唯一设备标识：使用客户端生成的 UUID 作为设备 ID，设备公钥用于验证身份和加密通信。

同步版本控制：乐观锁版本号 + 软删除，支持冲突检测和增量同步。

最小化个人信息：服务器不需要知道密码标题、用户名等，所有敏感数据都在加密 blob 中。

2. 服务器端表结构
   表 1：registered_devices（已注册设备）
   字段名	类型	说明
   device_id	TEXT (PK)	设备 UUID，客户端生成，全局唯一
   device_name	TEXT	设备名称（如 "Pixel 7"）
   public_key	TEXT NOT NULL	RSA 公钥（Base64）
   signature	TEXT	设备私钥对 device_id + public_key 的签名（可选，用于身份验证）
   registered_at	TIMESTAMP	注册时间
   表 2：encrypted_data_keys（Data Key 密文）
   字段名	类型	说明
   target_device_id	TEXT (PK)	接收 Data Key 的设备 ID（即该密文是给谁的）
   encrypted_data_key	TEXT NOT NULL	用目标设备公钥加密的 Data Key（Base64）
   encrypted_by_device	TEXT	加密该 Data Key 的设备 ID（谁加密的，可空）
   created_at	TIMESTAMP	创建时间
   表 3：sync_records（同步的密码记录）
   字段名	类型	说明
   record_id	TEXT (PK)	密码记录 UUID，与客户端保持一致
   device_id	TEXT NOT NULL	最后修改该记录的设备 ID
   encrypted_blob	TEXT NOT NULL	用 Data Key 加密的完整记录密文（Base64），包含所有字段（title, username, password, notes, url, tags 等）
   sync_version	INTEGER NOT NULL	乐观锁版本号，每次修改 +1
   operation	TEXT	'create' / 'update' / 'delete'
   server_updated_at	TIMESTAMP	服务器接收时间
   client_updated_at	TIMESTAMP	客户端最后修改时间（用于增量拉取）
   说明：

encrypted_blob 是客户端用 Data Key 加密后的序列化数据（例如 JSON 或 Protobuf），格式由客户端定义。服务器完全不知道内部结构。

operation = 'delete' 时，encrypted_blob 可为空，但保留记录以实现软删除同步。

客户端在拉取增量时，可根据 client_updated_at 和 sync_version 判断更新顺序。

表 4：sync_metadata（设备同步状态）
字段名	类型	说明
device_id	TEXT (PK)	设备 ID
last_pull_time	TIMESTAMP	该设备最后一次拉取的时间戳，用于增量拉取
last_push_time	TIMESTAMP	该设备最后一次推送的时间戳
3. 数据流与同步过程
   3.1 初始化第一台设备（例如手机）
   生成设备 ID、RSA 密钥对、随机 Data Key。

本地数据库存入设备信息，用本机公钥加密 Data Key 并保存到本地 devices 表。

向服务器注册设备：POST /register，上传 deviceId, deviceName, publicKey。

上传本机的加密 Data Key：POST /data-keys 存入 encrypted_data_keys。

之后所有添加/修改的密码记录，本地加密后通过 POST /sync/push 上传到 sync_records。

3.2 添加第二台设备（例如 CLI）
新设备生成自己的设备 ID、RSA 密钥对。

注册到服务器（上传公钥）。

授权流程：

新设备请求已在线设备（如手机）获取 Data Key。可以在服务器上标记“待授权”，或直接由用户在两台设备间通过二维码/手动确认。

已授权设备（手机）从服务器拉取新设备的公钥，用该公钥加密 Data Key，然后上传到 encrypted_data_keys（target_device_id = 新设备 ID）。

新设备拉取自己的 encrypted_data_key，用本地私钥解密得到 Data Key。

新设备执行增量拉取 (GET /sync/pull?since=0)，获取所有历史密码记录密文，用 Data Key 解密后存入本地数据库。

3.3 日常同步（以安卓端为例）
推送：本地记录修改后，调用 POST /sync/push，携带 recordId, encryptedBlob, syncVersion。服务器检查版本冲突，若成功则更新。

拉取：定时或手动触发 GET /sync/pull?since=<lastPullTime>，获取其他设备的修改。客户端逐条处理，更新本地数据库（可能涉及冲突合并）。

删除：软删除，设置 operation='delete'，客户端同步后标记 isDeleted=true。

4. 安全保证
   端到端加密：所有密码记录的内容由 Data Key 在客户端加密，服务器仅保管密文。

Data Key 保护：Data Key 明文只出现在设备内存中，用设备公钥加密传输，服务器无法解密。

设备身份：公钥为设备标识，可选使用私钥签名请求，防止设备仿冒。

主密码不联网：主密码只用于本地派生 K_master 解锁私钥，绝不离开设备。

零知识原则：即使服务器被攻破，攻击者只能得到加密的 blob 和加密的 Data Key，没有私钥就无法解密。

5. 服务器实现建议
   轻量级 REST API：用你喜欢的语言（Rust Actix-web、Node.js Express、Go）快速实现几个端点。

数据库：SQLite（初期足够）或 PostgreSQL。

认证：简单的 token 或基于设备公钥的签名认证（例如，客户端用私钥签名请求体+时间戳，服务器用公钥验签）。

API 端点：

POST /register

GET /data-key/{deviceId} → 获取给本机的加密 Data Key（新设备授权后拉取）

POST /data-key/{targetDeviceId} → 已授权设备上传加密的 Data Key

POST /sync/push

GET /sync/pull?since=<timestamp>

这个设计完全符合多设备端到端加密同步的要求，你可以直接基于此搭建服务器。若需要具体 API 代码示例（如 Rust Actix-web 骨架），我可以进一步提供。
